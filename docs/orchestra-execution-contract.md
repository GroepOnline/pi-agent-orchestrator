# Orchestra execution contract

Status: vNext foundation, contract version 1.

This document defines the ownership and correlation boundary between `pi-missions` and `pi-agent-orchestrator`.

## Ownership

`pi-missions` owns durable mission state across process/session restarts:

- mission state machine and feature lifecycle
- checkpoints and replay/restart
- logical retry/attempt budgets across executions
- durable cancellation intent
- durable artifact references and evidence
- idempotent recovery decisions after restart

`pi-agent-orchestrator` owns one execution-local orchestration:

- execution strategy resolution
- worker membership
- local step dependency ordering
- parallel fan-out and local workflow sequencing
- live steering and cancellation of the current execution
- result aggregation/delivery
- execution-local timing, usage and diagnostics

An Orchestra Run must therefore never become the canonical durable recovery record for a mission. Run history may be persisted for observability, but `pi-missions` remains the authority that decides whether another execution attempt exists after failure/restart.

## Identity hierarchy

For a mission-backed execution the durable caller supplies:

```text
missionId
  └── taskId          (normally a pi-missions feature/task id)
      └── attemptId   (one logical execution attempt)
          └── idempotencyKey
```

The four mission fields are all-or-nothing.

### attemptId

`attemptId` identifies one logical execution attempt.

- Transport retries, reconnects or duplicate delivery of the same logical attempt MUST reuse the same `attemptId`.
- A mission-level retry that intentionally starts a fresh execution MUST allocate a new `attemptId`.
- Orchestra does not increment or reinterpret mission attempt counters.

### idempotencyKey

The canonical key is generated by `buildMissionExecutionIdempotencyKey()`:

```text
orchestra:v1:mission:<missionId>:task:<taskId>:attempt:<attemptId>
```

Components are URI encoded.

The key is deterministic and contains no session/process timestamp. A transport duplicate with the same logical identity therefore maps to the same key. A new logical attempt maps to a different key.

RunManager will use this key to deduplicate Run creation once the vNext Run layer lands. Durable retry policy remains in `pi-missions`.

## Request envelope

`OrchestraExecutionRequest` contains:

- `contractVersion`
- user/execution task
- correlation identity
- optional typed input
- optional artifact references

The envelope intentionally does **not** contain durable checkpoint/recovery state.

## Result envelope

`OrchestraExecutionOutcome` returns:

- execution-local `executionId`
- the original correlation identity
- terminal status: `completed | failed | cancelled`
- result payload
- artifact references
- execution-local error metadata and timing

`pi-missions` consumes this outcome and decides how durable mission state changes.

## Artifact boundary

Artifacts cross the boundary by reference. The contract supports file, branch, URL, note and opaque references.

Orchestra may produce local artifacts. It does not become the canonical long-lived artifact database. The durable mission layer decides what references/evidence are persisted for replay and recovery.

## Cancellation

Cancellation has two levels:

1. `pi-missions` records durable cancellation/mission intent.
2. The active Orchestra execution receives a cancellation request and stops currently active workers / prevents waiting local steps from starting.

A local cancellation event alone is not sufficient durable mission state after restart.

## Retry and side-effect invariant

Mission replay must not accidentally create duplicate executions because of a repeated transport request.

Required invariant:

> same `missionId + taskId + attemptId` => same idempotency key => same logical Orchestra execution.

A deliberate new mission attempt must have a new `attemptId`.

## Scope of this contract

This contract deliberately does not yet define the full vNext `OrchestraRun`, strategy or workflow schemas. Those are introduced by CHE-132/CHE-134/CHE-133. This file locks the cross-repository boundary those implementations must respect.
